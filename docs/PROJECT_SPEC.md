# 知微 ZhiWei — V1.0 产品设计规格与开发实施方案

> 项目代号：ZhiWei  
> 产品名称：知微  
> 使用者：木川  
> 产品形态：Telegram 私人 AI 助手  
> 项目版本：V1.0  
> 开发语言：Python  
> 核心定位：具有朋友式人格和长期记忆能力的私人 AI 伙伴  
> 开发原则：先稳定、后智能；先记忆、后主动；隐私优先。

---

# 第一部分：项目定位与产品设计

## 1.1 项目背景

知微不是一个普通的 Telegram 问答机器人，也不是简单地把大模型 API 接入 Telegram。

它希望成为一个能够长期了解使用者的私人 AI 伙伴。

随着交流次数增加，知微应该逐渐了解：

- 使用者的兴趣爱好。
- 使用者的学习和工作经历。
- 使用者正在进行的项目。
- 使用者的生活习惯和偏好。
- 使用者的重要经历和计划。
- 使用者身边的人物及其关系。
- 使用者近期关注的事情和变化。

知微需要具备跨会话的信息延续能力，而不是每次对话都从零开始。

## 1.2 产品核心定位

**知微 = AI 对话伙伴 + 个人长期记忆 + 个人经历管理。**

V1.0 重点不是让知微拥有大量工具，而是先建立三个基础能力：

1. 能够自然地交流。
2. 能够正确地记住信息。
3. 能够在合适的时候调用记忆。

## 1.3 产品设计原则

| 原则 | 具体要求 |
|---|---|
| 自然交流 | 不采用机械客服式回答 |
| 人格一致 | 不同会话保持稳定的基本人格 |
| 长期记忆 | 跨会话保留经过允许的信息 |
| 记忆可控 | 用户能够查看、确认、修改和删除 |
| 隐私优先 | 敏感信息未经确认不得写入长期记忆 |
| 模块解耦 | 模型、记忆、Bot、数据库相互独立 |
| 可扩展 | 为后续智能体、工具调用和主动任务预留接口 |
| 成本控制 | 优先使用免费 API 和免费云端资源 |

# 第二部分：V1.0 功能需求

## 2.1 功能模块总览

V1.0 分为六个核心模块。

| 模块 | 核心功能 | 优先级 |
|---|---|---|
| Telegram Bot | 消息收发、命令、交互按钮 | P0 |
| AI 对话系统 | 模型调用、多轮对话、人格提示词 | P0 |
| 会话管理 | 历史记录、上下文管理 | P0 |
| 长期记忆系统 | 记忆提取、审核、保存、检索 | P0 |
| 个人画像系统 | 兴趣、经历、偏好、人物档案 | P1 |
| 系统管理 | 模型切换、配置、日志、健康检查 | P1 |

## 2.2 Telegram Bot 模块

### 基础功能

- 创建并初始化 Bot。
- 接收用户文字消息。
- 调用 AI 助手生成回答。
- 返回模型回复。
- 支持多轮连续交流。
- 支持 Telegram 命令。
- 支持 Inline Keyboard 交互按钮。

### 命令设计

| 命令 | 功能 |
|---|---|
| `/start` | 初始化知微 |
| `/chat` | 开始聊天 |
| `/new` | 开启新的对话会话 |
| `/memory` | 查看记忆管理入口 |
| `/profile` | 查看个人画像 |
| `/people` | 查看已确认的人物档案 |
| `/history` | 查看历史对话 |
| `/model` | 查看或切换模型 |
| `/settings` | 系统设置 |
| `/help` | 帮助说明 |

### 交互原则

知微的主要入口始终是自然语言聊天。

命令只是辅助功能，不应该让用户必须记住大量命令才能使用。

## 2.3 AI 对话模块

### 人格定位：Friend

知微采用朋友型人格。

人格特点：

- 自然、轻松、友善。
- 有自己的交流风格。
- 能够认真倾听。
- 不刻意讨好用户。
- 不机械地重复用户的话。
- 能够提供自己的分析和观点。
- 适当使用幽默，但不过度。
- 在不同场景下调整交流方式。

### 人格行为规范

| 场景 | 交流方式 |
|---|---|
| 日常聊天 | 轻松自然 |
| 用户分享经历 | 认真倾听、适当回应 |
| 学习问题 | 清晰解释、耐心交流 |
| 项目讨论 | 理性分析、提出建议 |
| 用户寻求意见 | 给出独立观点和理由 |
| 用户情绪低落 | 温和回应，不随意说教 |
| 用户讨论计划 | 帮助整理思路和目标 |

### 系统提示词设计

人格提示词独立存放，不与业务代码混合。

建议分为：

1. 核心身份。
2. 人格特点。
3. 交流风格。
4. 用户背景。
5. 长期记忆使用规则。
6. 隐私保护规则。
7. 回复行为规范。

注意：

知微不能为了表现得像朋友而虚构自己拥有真实的人类生活经历、线下活动或现实关系。

## 2.4 多轮对话管理

V1.0 需要实现：

- 保存每条用户消息。
- 保存每条 AI 回复。
- 维护会话 ID。
- 支持多轮上下文。
- 支持开启新会话。
- 支持历史会话查询。
- 控制上下文长度。

建议采用：

**最近消息 + 相关长期记忆 + 当前用户消息**

组成模型输入。

不要将所有历史聊天记录无限制地发送给模型。

建议初始参数：

- 最近 10～20 条消息作为上下文。
- 根据模型实际上下文限制动态调整。
- 长期记忆按相关性检索。
- 对话历史永久保存与否由用户设置决定。

# 第三部分：长期记忆系统设计

这是知微 V1.0 最重要的模块。

## 3.1 记忆系统设计目标

知微不应该只保存聊天记录。

它需要从交流中发现具有长期价值的信息，并逐步形成结构化的个人知识库。

记忆系统采用：

**自动识别 + 记忆候选 + 用户确认 + 长期保存 + 相关检索。**

注意区分：

- 对话历史：用户说过什么。
- 记忆候选：AI 认为值得保存的信息。
- 长期记忆：经过保存规则允许后，真正进入记忆库的信息。

三者不能混为一谈。

## 3.2 记忆分类

### A. 个人画像 Profile

记录长期相对稳定的信息：

- 兴趣爱好。
- 学习方向。
- 技能和知识背景。
- 长期目标。
- 交流偏好。
- 长期项目。

### B. 经历记忆 Experience

记录重要经历：

- 过去的学习经历。
- 项目开发过程。
- 重要决定。
- 个人成长经历。
- 重要事件。
- 阶段性成果。

### C. 人物关系 Relationship

记录使用者主动介绍的人物：

- 人物称呼。
- 人物身份。
- 与使用者的关系。
- 相关共同经历。
- 关系变化。
- 信息来源。

禁止仅凭聊天中的一句话就擅自推断两个人的真实关系。

### D. 情境记忆 Context

记录短期状态：

- 最近正在做什么。
- 当前项目进展。
- 近期计划。
- 待处理事项。
- 最近关注的话题。

情境记忆应支持过期、更新和归档。

### E. 偏好记忆 Preference

记录用户明确表达的长期偏好：

- 技术选择。
- 学习方式。
- 交流习惯。
- 内容风格。
- 工具使用偏好。

## 3.3 混合记忆机制

采用以下规则：

| 信息类型 | 处理方式 |
|---|---|
| 普通、低风险、明确的长期偏好 | 可按规则自动保存，并通知用户 |
| 明确的长期项目状态 | 可自动更新已有低风险记忆 |
| 重要个人经历 | 生成候选，等待确认 |
| 人物关系信息 | 生成候选，等待确认 |
| 敏感个人信息 | 不自动保存，必须明确确认 |
| AI 推测的信息 | 不作为事实保存 |
| 临时闲聊 | 不自动转为长期记忆 |
| 用户明确要求记住 | 生成记忆候选并进入确认流程 |

所有自动保存行为必须可追溯、可撤销。

## 3.4 记忆处理工作流

```text
用户发送消息
      |
      v
AI 理解消息
      |
      v
检索相关历史记忆
      |
      v
生成自然语言回复
      |
      v
记忆提取模块
      |
      v
判断是否值得长期保存
      |
      v
生成结构化记忆候选
      |
      v
检查隐私和保存权限
      |
      +-----------------------+
      |                       |
      v                       v
低风险、明确的信息       重要或敏感信息
      |                       |
      v                       v
按规则自动保存          Telegram 确认
      |                       |
      |                 +-----+-----+
      |                 |           |
      |                 v           v
      |               同意         拒绝
      |                 |           |
      v                 v           v
      +------------> 更新记忆库    丢弃候选
```

## 3.5 记忆确认交互

当知微发现重要信息时，向用户发送：

> 木川，我觉得刚才提到的这件事情可能值得保留为长期记忆。
>
> 我准备记录：
>
> - 分类：项目经历
> - 内容：正在开发一个私人 AI 助手。
> - 用途：以后交流项目时可以参考。
>
> 你希望保存吗？

提供按钮：

- 确认保存
- 修改内容
- 暂不保存
- 永久不再询问此条信息

最后一个选项仅针对该条候选，不代表关闭整个记忆系统。

## 3.6 记忆检索

用户发送消息时：

1. 获取当前用户消息。
2. 提取查询意图和关键词。
3. 检索相关个人记忆。
4. 根据相关性和时间排序。
5. 将必要记忆加入模型上下文。
6. 生成回答。

第一阶段可以采用：

- PostgreSQL 全文检索。
- 分类筛选。
- 关键词匹配。
- 时间和重要性排序。

后续再考虑 pgvector 语义检索。

## 3.7 记忆管理功能

用户应该能够：

- 查看全部记忆。
- 按类别筛选。
- 查看记忆来源。
- 修改记忆内容。
- 删除记忆。
- 查看待确认记忆。
- 查看最近新增记忆。
- 暂停自动记忆。

必须保证删除操作真正删除对应的持久化记录，而不是仅在聊天界面隐藏。

| 异步数据库驱动 | asyncpg |
| AI 模型 | Gemini API |
| 备用模型 | OpenRouter |
| 部署平台 | Render |
| 数据库托管 | Neon |
| 测试 | pytest、pytest-asyncio |
| 代码规范 | Ruff |

实际部署前，需要验证 Python 版本、依赖版本和各服务的免费计划。

## 4.2 模块架构

```text
Telegram
   |
   v
Telegram Adapter
   |
   v
Application Service
   |
   +----------------------+
   |                      |
   v                      v
Conversation Service   Memory Service
   |                      |
   v                      v
Assistant Service      Memory Manager
   |                      |
   v                      v
LLM Router             Memory Retriever
   |                      |
   v                      v
Model Adapter          PostgreSQL
   |
   v
Gemini / OpenRouter
```

## 4.3 核心架构原则

### 模型层独立

不允许在 Telegram Handler 中直接编写 Gemini API 调用逻辑。

应通过统一模型接口调用。

### 记忆层独立

记忆提取、审核、保存和检索应该是不同的业务职责。

### Bot 层独立

Telegram 只是交互入口。

以后即使增加 Web 页面，也不应该重写核心 AI 业务逻辑。

### 数据访问独立

数据库操作通过 Repository 或数据访问层完成，避免业务逻辑直接编写大量 SQL。

- 不在日志中输出 API Key 和 Bot Token。
- 重要记忆必须保留来源信息。

# 第八部分：安全与隐私设计

这是项目的强制要求。

## 8.1 用户访问控制

- V1.0 只允许指定 Telegram 用户使用。
- 通过 Telegram User ID 进行身份校验。
- 不允许其他用户访问个人数据。
- Webhook 使用 Telegram Secret Token 验证。
- 不在公开接口暴露记忆内容。

## 8.2 密钥管理

以下信息必须通过环境变量配置：

```env
TELEGRAM_BOT_TOKEN=
TELEGRAM_USER_ID=
TELEGRAM_WEBHOOK_SECRET=

GEMINI_API_KEY=
GEMINI_MODEL=

OPENROUTER_API_KEY=
OPENROUTER_MODEL=

DATABASE_URL=
```

禁止：

- 将密钥写进 Python 源码。
- 将 `.env` 提交到 GitHub。
- 在异常日志中输出密钥。
- 将密钥发送给大模型。

## 8.3 记忆隐私

必须实现：

1. 用户能够查看保存了什么。
2. 用户能够修改保存内容。
3. 用户能够删除指定记忆。
4. 敏感信息未经确认不能进入长期记忆。
5. AI 推断不得自动成为事实。
6. 人物关系必须具有信息来源。
7. 删除操作需要同步处理关联数据。

## 8.4 模型数据边界

免费模型服务可能有不同的数据保留和训练政策。

因此：

- 不向模型发送无关个人信息。
- 检索记忆时只提供必要内容。
- 不把完整数据库交给模型。
- 不发送密码、API Key 等秘密。
- 重要私人记忆应在用户确认后才允许进入记忆库，但仍需注意发送给模型时的服务商数据政策。

# 第九部分：部署方案

## 9.1 目标部署

```text
Telegram Bot
      |
      v
Telegram Webhook
      |
      v
Render
Python + FastAPI + aiogram
      |
      +----------------+
      |                |
      v                v
Gemini API       OpenRouter
      |
      v
Neon PostgreSQL
```

## 9.2 部署要求

- 使用 GitHub 管理代码。
- Render 部署 Python Web Service。
- Neon 提供 PostgreSQL。
- Telegram 配置 HTTPS Webhook。
- 通过环境变量管理生产环境配置。
- 使用 Alembic 执行数据库迁移。
- 提供健康检查接口。
- 实现异常日志和服务恢复机制。

## 9.3 免费部署的限制

必须接受以下现实：

## 10.1 Telegram 基础测试

- Bot 能否正常启动。
- 能否接收消息。
- 能否正常回复。
- 是否支持多轮对话。

## 10.2 模型测试

- Gemini 是否能够正常调用。
- OpenRouter 是否能够正常调用。
- 主模型失败是否能够切换备用模型。
- API 限流是否能够正确处理。
- 模型异常是否会导致 Bot 崩溃。
- 回复过长时是否能够正确分段。

## 10.3 记忆测试

测试场景：

1. 用户明确介绍一项长期兴趣。
2. AI 生成记忆候选。
3. 用户确认保存。
4. 用户开启新会话。
5. 用户询问之前介绍的兴趣。
6. AI 能够准确检索。
7. 用户修改记忆。
8. 再次检索时返回更新后的内容。

## 10.4 隐私测试

- 用户拒绝保存后，候选不得进入正式记忆。
- 用户删除后，记忆不能再次被检索。
- 未授权用户无法访问数据。
- 敏感信息不会被自动写入长期记忆。
- 记忆候选不能绕过确认机制。
- Webhook 无效请求不能进入消息处理流程。

## 10.5 最终验收标准

V1.0 只有满足以下要求才算完成：

- Telegram Bot 能够稳定完成基本聊天。
- 支持多轮上下文。
- 具有一致的知微人格。
- 对话记录能够持久保存。
- 能够提取记忆候选。
- 能够执行确认、拒绝和修改。
- 能够跨会话检索正式记忆。
- 能够管理个人画像。
- 能够保护人物关系信息。
- 能够查看和删除记忆。
- 能够在个人电脑关闭的情况下使用。
- 具备基础异常处理和安全验证。

# 第三部分：V1.0 开发过程中的关键决策

## 1. 不要过早引入 LangGraph

第一版使用普通 Python 服务层即可。

理由：

- 当前核心是对话和记忆管理。
- 业务流程还比较明确。
- 过早使用复杂工作流会增加调试成本。

等到需要多步骤任务、主动任务、复杂工具调用时，再引入 LangGraph。

## 2. 不要一开始就做向量数据库

先使用 PostgreSQL 结构化存储和基础检索。

当记忆规模增加、关键词检索无法满足需求时，再考虑 pgvector。

## 3. 记忆提取不能完全依赖模型

大模型负责提出记忆候选。

Python 业务逻辑负责：

- 校验数据结构。
- 检查用户权限。
- 执行敏感信息规则。
- 管理确认状态。
- 决定是否写入数据库。

模型不能自行绕过业务规则。

## 4. 不要让免费模型决定整个系统的架构

模型服务需要可替换。

无论以后选择 Gemini、OpenRouter 还是其他模型，都应该尽量不影响核心业务逻辑。

## 5. 第一版优先保证记忆准确性

宁愿少记一些，也不要错误记忆。

尤其是人物关系、经历和个人偏好。
